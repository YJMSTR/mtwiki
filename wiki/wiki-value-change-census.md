# 变值普查：生成代码仿真器中的值变化测量纪律

## 概述

生成代码仿真器里最常见的优化幻觉是："大多数写操作写的都是旧值，跳过它们就能省时间"。这个判断的前半句（不变写比例高）在很多采样式电路 + 整数工作负载上**恰好为真**，但它是工作负载×站点种群的联合属性，**不能从任何间接证据推断**——只能到真实发射的每个存储站点上去数。

**变值普查（value-change census）**是一种一次性、报告性质的插桩：在代码生成的存储站点处内联计数器，把 RHS 物化一次进临时变量，与当前值比较后计入 changed/unchanged（可按位宽分类），然后**照常无条件存储**。它不改任何行为，只回答一个问题："如果我在这里发射 compare+branch，命中率会是多少？"

本文提炼这套测量的纪律：为什么必须先普查（§1）、站点如何界定（§2）、计数器如何跨编译单元工作（§3）、原子性如何选择（§4）、插桩如何引爆编译器（§5）、如何证明比例是稳态（§6），最后是一份可迁移的检查清单（§7）。案例数据来自多线程 RTL 仿真器 gsim-mt（见文末）：在约 25.7 万个合格寄存器状态存储站点上实测 96–97% 写入不变值——而这个数字随后被 A/B 证明**不足以**支撑条件存储收益（见 [[wiki-conditional-store-elision]]），恰恰说明普查是必要输入而非充分结论。

---

## 1. 反事实不可推断：为什么必须先普查

一切跳过类优化的预期收益 = 可跳过比例 × 跳过单价。第二个因子可以静态估计，第一个因子看起来"可以用别的数字近似"——这正是事故来源。

### 1.1 间接证据的典型误用

案例中的一个真实修正：稀疏执行器与稠密执行器的指令数比值为 7.4x，直觉上"稀疏执行器跳过了 86% 的指令，说明大部分计算（包括写）是无效的"。评审后明确记录：**这是执行器对执行器的比较，对存储值的分布不构成任何界**——两个执行器做的是不同的工作集合，指令比值不能外推到任何一个具体站点的不变写概率。若据此发射条件存储，就是在用循环论证支撑代码生成决策。

从比值推断分布之所以循环：不变写比例是"站点种群 × 工作负载轨迹"的联合经验量。换了站点界定（哪些存储算数）、换了工作负载、换了电路采样方式，比例都会变。唯一合法的测量点就是**最终会被插桩的那些站点本身**。

### 1.2 普查先于发射（census before emit）

由此得到纪律：**任何"跳过无效工作"类的代码生成改动，先做纯计数普查，再做执行形式**。普查 knob 与执行 knob 可以共用一个开关分级（案例：同一环境变量 1=census、2=exec+counters、3=exec 无计数器），但 census 模式必须是默认路径——任何真值（truthy）但 <2 的取值都落回 census。这样收益预期（比例）与收益实现（跳过代码）在同一个站点定义下测量，不会出现"普查的站点"和"发射的站点"错位。

> 一条被完整记录的教训：A/B 否决了"在全部站点动态 compare+branch"这一实现族之后，报告里仍点名了两个**未经普查**的候选方向（读侧无效负载普查、静态无消费者写省略）——否决一个实现不等于关闭一个方向，但**开启任何新方向的第一步仍然是普查**。

## 2. 站点界定：结构性分类在生成时完成

普查的价值取决于"数的是不是将来要改的站点"。界定必须在代码发射时按**节点结构**做，而不是事后对生成文本做模式匹配。

### 2.1 合格与排除的分类

案例的界定（寄存器状态存储）：

| 类别 | 结构特征 | 处理 |
|---|---|---|
| **reg-next 站点** | `reg$NEXT = rhs`（NODE_REG_DST，存在有效 regNext） | 插桩计数 |
| **reg-commit 站点** | `reg = reg$NEXT`（NODE_REG_SRC 提交存储） | 插桩计数 |
| 数组 / 子数组拷贝 | 下标存储、聚合拷贝 | 排除，生成时计数 |
| 宽目标 | >64 位多字目标 | 排除，生成时计数 |
| 非整成员左值 / 复合语句 | 部分写、regReset 复合 | 排除，生成时计数 |
| 内存写端口 | NODE_WRITER/READWRITER | 排除（本身有条件语义） |

两个要点：

1. **排除也要数**。生成器在普查结束时打印站点统计（插桩 N = reg-next a + reg-commit b；排除 array/wide/compound/memport 各多少）。这份"站点普查的普查"让后续读者能判断结果覆盖了多少存储总量——案例中 25.7 万合格站点之外还有约 2.5 万排除站点，不声明这一点的人将来会把 96% 误读成"所有写的 96%"。
2. **位宽分类**。计数器按宽度类（w1/w8/w32/w64）分桶。位宽决定 compare 与 store 的相对价格（§4、[[wiki-conditional-store-elision]] §2）：单字比较便宜，多字排除在外。没有宽度分桶的总量数字无法支撑任何价格论证。

### 2.2 普查模式不得改变行为

census 模式的发射形态是：RHS 物化一次进块作用域临时变量 → 计数 → **照常无条件存储**。与普通存储的唯一差别是计数器。这条"无行为变化"主张要用等价性验证背书：案例在 knob 开启后于若干小 FIR 设计 + 完整稠密配方上验证输出恒等，并在每次测量侧运行体系结构精确参考（NEMU）门禁。插桩如果改变了行为，普查数字本身就不可信。

## 3. 计数器工程：跨编译单元的 inline 计数器

生成代码仿真器把模型切成几十到上千个 `.cpp` 分片并行编译。插桩站点落在各分片里，而汇总报告（通常挂在析构/退出钩子上，如 profile dump 路径）落在另一个分片——**计数器必须在多个翻译单元间共享**。

### 3.1 惯用形态

C++17 起的标准做法：在**生成的公共头文件**里声明 namespace 作用域的 `inline` 变量：

```cpp
// 生成的 SimTop.h（公共头，所有分片包含）
inline std::atomic<uint64_t> mtDenseStoreSkipTotal{0};
inline std::atomic<uint64_t> mtDenseStoreSkipChanged{0};
inline std::atomic<uint64_t> mtDenseStoreSkipUnchanged{0};
inline std::atomic<uint64_t> mtDenseStoreSkipTotalW1{0}, /* w8/w32/w64... */;
```

分片内站点用 `fetch_add(1, std::memory_order_relaxed)` 递增；报告侧在进程退出时 `load(relaxed)` 汇总打印。松序足够：计数器只求最终总和正确，不求任何顺序保证。

### 3.2 发射器转义陷阱

生成器用 printf 风格的发射函数（如 `emitBodyLock`）把 C 代码写成字符串时，**生成代码里字面的 `%` 必须写成 `%%`**——计数报告里的 `%llu`、`%.4f` 格式串是最常见的踩坑点。案例中该问题（连同 spawn-guard 完整性）由评审在**测量之前**捕获；漏网时症状是编译器 `-Wformat-insufficient-args` 告警刷屏（一次实测构建中同类格式告警超过 1800 条）。规则：生成带格式串的代码时，把"转义告警清零"当作发射器的门禁，而不是等编译日志提醒。

## 4. 计数器原子性：单写者分析与争用灾难

### 4.1 灾难形态：每站点原子 RMW

对计数器无脑上原子是最容易犯的"安全"错误。案例实测两级后果：

- **census 模式（可接受）**：全部站点共享少量全局原子计数器，总开销约 68x 减速。这是**报告性质**测量的固有价格——普查数字只依赖计数的正确性，不依赖跑得多快，慢 68x 换一个可信数字是划算的。
- **exec 模式（不可用）**：把条件存储与原子计数器同时发射（先发射的中间形态），结果是**不可测地慢**——数亿次每秒的存储事件 × 跨核原子 RMW 在共享计数器上线性化，构造性争用灾难；文本同时膨胀 36%。25 秒内无任何输出，回栈显示全部 worker 在池循环自旋（活锁式慢，非死锁）。教训：**测量计数器与被测执行形式必须彻底分离**——被测形态（mode 3）一个计数器都不带。

### 4.2 单写者分类：把原子降级为普通计数

并非每个站点都需要原子。调度器在生成时已经知道每个任务体归属哪个 worker：

| 站点类别 | 判定（生成时静态可得） | 计数器形态 |
|---|---|---|
| **单写者** | 站点所在体有唯一稠密 owner 且无冲突归属；或仅串行段执行（主线程独占） | 普通（非原子）递增 |
| **多写者** | 体浮动（无固定 owner）或存在冲突归属 | 原子 `fetch_add` |

案例的读侧普查按此分类每站点发射 plain/atomic 计数，并在生成日志打印 `single-writer=N atomic=M`。当 95%+ 站点落在单写者类时，普通计数器把普查开销从"每事件一次跨核 RMW"降到"每事件一次本地自增"——普查才在可承受开销内覆盖全部站点。

反过来，**单写者分析也是条件存储正确性论证的一部分**（见 [[wiki-conditional-store-elision]]）：`if (cur != tmp) cur = tmp;` 的省略语义要求比较与存储之间不存在并发写者覆盖窗口；唯一写者的字段上该论证成立，多写者字段上必须逐个审查。计数器原子性选择与跳过安全性论证共用同一份归属分析——一次分析，两处消费。

## 5. 插桩引爆编译器：-O3 爆炸与 -O1 回退

把数十万站点逐个包裹（临时变量物化 + 比较 + 计数 + 条件/无条件存储）不是均匀撒进所有分片——最热的分片集中了最多站点，单个 TU 的语句数与基本块复杂度被插桩放大数倍。在这样的"重度包裹 TU"上，激进优化器（`-O3` 的内联/展开/向量化组合）会进入超线性复杂度区：**案例中 2 个分片合计耗时 2 小时 47 分**，其余分片早已编完，整个并行构建被两颗最重的 TU 卡死。

应对纪律：

1. **插桩构建用 `-O1`**。普查数字不依赖优化级别——计数的是行为语义（值是否相等），不是优化后的指令流；优化级别只改变普查的**开销倍数**，不改变**比例**。为一次报告性质的测量付出优化器爆炸没有任何收益。
2. **被测执行形式的 A/B 必须回到生产优化级别**（案例 champion 构建 `-O3 -march=<target>`）。条件存储的代价（compare+branch、文本膨胀的 icache 税）只有在生产优化下才真实显现——`-O1` 下测出的"省略收益"会系统性高估。
3. **构建层面预防**：分片（shard）策略要给插桩构建留余量；最重 TU 的站点密度在生成日志里可见，可以在构建前预判哪几个分片需要降级编译或进一步切分。

> 与 [[wiki-chisel-and-essent]] 记录的 ESSENT 现象同源：直线化/全展开生成代码本身就已让编译时间"爆炸级"增长；插桩再乘一个站点数因子。生成代码仿真器的构建管线必须把"优化级别 × 插桩密度"当作二维决策，而不是固定 `-O3`。

## 6. 稳态验证：两个长度，一个结论

单一运行长度得到的比例无法区分**稳态属性**与**引导瞬态**：复位后预热阶段状态寄存器大量初始化写入，不变写比例天然偏低（或偏高，取决于站点定义），长跑后才是工作负载的真实面貌。

案例的双长度验证：

| 运行长度 | 总存储（事件数） | 不变写比例 |
|---|---:|---:|
| 短（≈基准 1x） | 8.57 亿 | **97.25%** |
| 长（10x） | 85.9 亿 | **96.30%** |

10 倍周期只把比例移动 0.95 个百分点 → 不变写是**稳态现象**，不是引导瞬态；同时它给出绝对规模感（约每周期 17 万次状态存储）。若两个长度给出的比例差异显著，正确做法是分区报告（瞬态段/稳态段各自的比例），而不是取平均——跳过类优化的收益只对稳态段有效。

## 7. 方法论检查清单

把上述纪律压缩成可迁移的清单：

1. **先问反事实能否推断**：任何间接比值（指令数比、活动率、翻转率）都不能替代站点级普查；分布只能测，不能推。
2. **站点界定即合同**：合格/排除分类在生成时按节点结构完成；排除站点同样计数并打印；插桩站点 = 将来要改动的站点。
3. **census 与 exec 分离**：census 模式行为恒等（计数后照常存储）；被测执行形态零计数器；两者可共用分级开关但默认落 census。
4. **计数器跨 TU 用 inline 原子 + 松序**；先做单写者归属分析，多数站点降级普通计数；共享全局原子只接受于报告性质运行（并预期数十倍开销）。
5. **发射器格式串转义（`%%`）列为门禁**；格式类编译告警清零。
6. **插桩构建 `-O1`，生产 A/B `-O3`**；监控最重 TU 的编译时长。
7. **双长度稳态验证**；比例差异大就分区报告。
8. **每条测量侧跑正确性门禁**（体系结构精确参考）；普查本身无行为变化也要验证。
9. **普查结论只回答"命中率"**，不回答"是否值得"——后者需要被测形态的 A/B（见 [[wiki-conditional-store-elision]]）与隔离纪律（见 [[wiki-ab-isolation-discipline]]）。
