# 指针迭代非确定性下的确定性代码生成

## 概述

当编译器或代码生成器用 `std::set<T*>` / `std::map<T*, V>` 存放图节点指针、且在至少一个决策点消费容器隐式供给的指针序时，输出就绑上了分配器、线程调度、ASLR 和系统内存状态。同一源码、同一环境、同一输入会产生不同的输出形状（调度、任务划分、生成代码布局），破坏 A/B 归因、证据转移和可复现构建。

这不是 C++ 特有的问题：任何"以对象地址/分配顺序为隐式排序键"的数据结构（哈希表迭代序、HashMap 遍历、字典序未定义的语言运行时）都有同一病灶。本文以图编译器为通用场景，用一个多线程 RTL 仿真器生成器（gsim-mt，见文末）的非确定性调查为案例，提炼可复用的机制分析、证据分层、调查方法论和修复模式。

---

## 1. 三个不能混淆的层次

非确定性分析必须先区分层次，否则会把良性现象当恶性修复、或把恶性问题当良性豁免。

| 层 | 现象 | 性质 | 判定依据 |
|---|---|---|---|
| **L1 生成器非确定性** | 同源码+同环境+同输入，生成不同输出（案例实测：同一输入五次生成得到 12,444 / 12,571 / 12,488 / 12,671 / 12,771… 个任务） | **恶性**：破坏 A/B 归因、证据转移、可复现构建 | 跨分配器/跨 run 指纹分叉 |
| **L2 运行时乱序** | 多 worker 完成时序、乱序子集随运行变化 | **良性（结构性论证 + 经验证据）**：引理论证独立条目可交换；短/长负载各 100 次重复端点全一致 | 端点不变性经验门 |
| **L3 打印行序** | 跨线程 printf 行序不同 | **豁免**：与既有参考工具行为等价、端点状态不可观测（只要没有任何机器可读判定消费行序） | 行序消费点审计 |

> **边界标注**：L2 的"良性"基于结构性论证（引理）和 100 次经验证据，**不是形式化证明所有时序下不变**。L2 的论证仅说明"在观察到的多个序变体下产出正确模拟"，不构成通用序不变性证明。

## 2. 机制：地址当排序键

### 2.1 容器默认行为如何引入指针序

`std::set<T*>` / `std::map<T*, V>` 在不提供自定义比较器时使用 `std::less<T*>`，对指针施加严格全序（常见实现中表现为地址值序）。指针序由此**隐式地**进入图算法的语义。

关键点：容器**必须**有一个严格弱序比较器才能工作。问题不在于"用了排序"，而在于"默认选择的是指针序"——一个运行时环境属性，不是内容属性。

### 2.2 序消费点分类

并非所有使用指针键容器的位置都有语义风险。按序是否被消费分为四类：

| 角色 | 典型位置 | 序是否影响语义 | 风险 |
|---|---|---|---|
| **仅成员性/查找** | 计数查找表、键查找、`visited` 去重、内层 set 的 find/count | 无关——只用 find/insert/count，不读序 | 无 |
| **序被消费（序即语义）** | `begin()` 取首元素做代表、指针序邻接集迭代构造合并向量、下标扫描贪心资格判定、`order` 字段比较 | 直接改变合并决策与结果形状 | **高** |
| **序消费但语义角色未定** | 指针序 map 逐组应用变换 | 组内顺序语义已证实；组间应用顺序是否影响结果**未证实** | 待定 |
| **非语义（桶/性能键）** | 指针求和做桶键、去重扫描 | 仅布局相关的桶分布/迭代顺序；分组由集合相等精确决定 | 低（继承自上游遍历不稳定） |

### 2.3 案例中的六个语义性序消费点

以下每个点都将指针序作为语义输入，是该案例非确定性的直接载体（均为图粗化/调度 pass 的典型结构）：

1. **`topoSort()` / `resort()`**：LIFO 栈前沿 + 指针序邻接集迭代 → 排序结果遍历序。随后 `orderAllNodes()` 把 `order` 赋为下标——遍历序从此成为数值，供下游比较消费。
2. **`mergeWhenNodes()` —— `condWait.begin()`**：指针序 set 的 `begin()` 取指针最小者作为合并条件发起者。
3. **`mergeWhenNodes()` —— `allSuper[0]`**：对选中的 mergeCond，按指针序遍历邻接集构造合并向量，`allSuper[0]` 成为合并目标（其余成员并入）。
4. **`mergeWhenNodes()` —— `whenMap` 迭代**：指针序 map 逐组应用合并（组内顺序语义已证实，组间未证实）。
5. **`mergeOut1`（下标逆向贪心）**：遍历邻接集，若任一邻居 `order < candidate->order` 则拒绝合并。合法性判定以不稳定 `order` 为输入。
6. **`mergeIn1`（下标正向贪心）**：同理，依赖不稳定 `order` 做资格判定。

**通用模式**：拓扑排序、贪心合并、代表选择（取 begin/首元素）、把遍历下标固化为 rank——这四类操作的输入一旦是指针序，输出形状就随内存布局漂移。

### 2.4 `std::set` 存指针的正当需求

容器选择本身不构成错误。`std::set` 在图算法中提供了三样被实际消费的属性：

| 属性 | 代码中的用法 | 风险 |
|---|---|---|
| **唯一性（幂等插入）** | 同一条边重复插入自动无效；大量 `find() == end()` 防重守卫 | 无 |
| **对数成员测试** | 数十处 `find` / `count` | 无 |
| **有序遍历** | 前沿弹出、合并循环、邻接集迭代 | **成为副作用的那个属性** |

问题是没有人为"序"设防。`std::unordered_set<T*>` 也不能解决问题——标准库自带指针哈希（`std::hash<T*>` 按地址散列），其迭代序同样环境依赖。

## 3. 证据分层

### 3.1 已证实的根机制

图遍用指针值做语义排序（指针序 set 的 `begin()`、首元素代表、指针序 map 迭代、LIFO 前沿），指针值随分配器/进程内存布局变化，输出随之变化。这是完整证据链定位的根因。

### 3.2 直接实测到的触发因素

| 因素 | 证据强度 | 证据 |
|---|---|---|
| **分配器策略差异** | **直接实测** | glibc vs jemalloc 产出不同形状（12,571 vs 12,671 个任务）；jemalloc 逐 run 漂移（每 run +100 任务）——分配器的 bin/arena 布局策略直接改变指针序 |
| 解析多线程交错 | 强相关 | 解析用 10 线程创建节点；线程 arena 分配顺序随时序变化（早晚簇翻转与大编译任务时段重合） |

### 3.3 可能触发、未独立证明

| 因素 | 边界 |
|---|---|
| ASLR | 仅证实已启用（randomize_va_space=2）。ASLR 整体平移基址但**可以不改变相对指针序**——同簇内逐 run 一致反而说明其在同系统状态下影响有限。未独立证明其为触发源。 |
| 系统内存状态 | 仅有时段相关性（大编译任务前后早晚簇翻转），未做因果隔离实验。 |

### 3.4 已排除

- arena 未初始化读取（`MALLOC_PERTURB_` 双值无影响）
- 输入变化（输入文件 sha256 不变）
- id 作为稳定键（同一逻辑节点 id 跨分配器不同：7145041 vs 7140539——**分配序计数器不是内容标识**）

### 3.5 为什么指针序形状质量好（假设）

**假设（未经独立实验证实）**：指针序与分配/创建顺序相关（顺序分配时地址单调），创建顺序又与解析/源码顺序相关；解析线程分块认领工作，使语义邻近的节点在遍历时被连续处理——一种意外的局部性。该假设解释了为何内容键替代存在形状税（实测 +12.3%～+24.6%，见 §5.1），以及为什么 exact replay 需要**记录**而非**推导**它。

## 4. 调查方法论（可复用）

### 4.1 同代双生（Same-Generation Twin A/B）

一次生成 → 克隆目录 → 只改目标差异 → `diff -qr` 证明隔离。适用于"同一输出上的代码变体"比较。

> 案例：批量扫描协议判决用此法验证 1,226 个生成文件中仅 23 行不同——差异恰好等于改动本身。

### 4.2 归一化输出指纹

对输出的结构要素（边表 + 层次表 + 分配表 + worker 数组）做 sha256，排除纯布局字段。分别生成的对照/候选必须过此指纹门才能做性能归因，否则计时结论作废——**你在比较两个不同的程序**。

### 4.3 遍边界规范化指纹二分（Canonical Hash Bisection）

调试开关：每个图遍（pass）边界输出"成员名+排序端点名（排除 id/地址）"的流式哈希，二分定位首个分叉遍。顺序敏感记录单独哈希，区分"内容分叉"与"仅遍历分叉"。

> 案例：用此法把分叉定位到条件合并遍（`coarsen.when`），并在拓扑排序遍发现一个"死内容分叉"（死节点内容不同，死代码消除后收敛）——首个真实分叉与首个可见分叉不是同一个。

### 4.4 ABBA + 指纹门

任何分配器/环境 A/B 都必须先验证产出物指纹一致，否则计时结论作废。

> 案例：jemalloc 调研的全部早期数据因四轮产出互不相同（12,571/12,671/12,771/12,571）而废弃——先看指纹再看表，能省掉整轮无效计时。

## 5. 修复模式

### 5.1 内容键比较器 + 带告警的 id 回退

**模式**：将所有语义排序点的比较器从默认指针序替换为内容序，末位用稳定标识做 tie-break。

**案例实现**（`SuperNodeStableLess` 比较链）：`源码行号 → 首成员名 → 成员名列表 → 依赖度 → id`。

**关键约束**：

1. **内容键本身不保证唯一**。行号可被分裂节点共享、空成员节点的键全为空。任何内容键都必须有末位 tie-break。
2. **末位回退必须能区分所有同时存活的 distinct 节点**（严格弱序），否则 set 会把键相等的节点当作同一元素去重——**静默丢节点，是正确性事故**。
3. **案例的末位回退是分配序 `id`**，而 id 是分配器不稳定的。回退被命中时该平局组的顺序重新变为非确定。实现以一次性 stderr 告警（`[stable-order] id fallback hit`）暴露此事件——**回退命中必须可观测**。

**实测代价**（同一负载、同 session 基线）：

| 修复 | 确定性 | 长负载耗时 | 形状税 |
|---|---|---|---|
| 指针序（默认，最快） | ✗（实测非确定） | **6,094.4ms** | -（基准） |
| 行号键（已采用为可选项） | ✓ 跨分配器指纹一致 | 6,843.2ms | **+12.3%** |
| 名字键 | ✓（4 路指纹全同） | 7,753.3ms | +24.6% |
| seed 首遍历重放 | ✓ 跨分配器一致 | 8,073.0ms | +32.0% |

> 注：不同行测量日期不同，税值以各自同 session 的指针序基线计算。跨日比较只作定性参考。

**为什么零税只有 exact replay**：输出形状是全部重排点结果的路径函数；任何"策略型"固定序（名字/行号）都只是近似指针序的质量。要拿到它只能**记录**那次运行的全部重排结果（见 §5.2）。确定性本身没有免费的午餐——这是"确定性 vs 质量"的真实权衡，不是实现不到位。

### 5.2 exact replay（记录重排结果）

**模式**：逐点记录首次生成的遍历排列 + 输入图哈希，重放时强制按记录排列执行。

**案例两代设计**：
- v1：钉住首个拓扑排序的排列（+32.0% 税，因仅钉首遍历、后续仍用不稳定序）——**只钉第一个非确定点是不够的**。
- v2：逐重排点排列记录 + 分组结果记录 + 逐点强制 + 每点验证。落地后跨分配器字节一致、零税（见 §9）。

### 5.3 冻结产物 + 三道门（交付哲学）

**模式**：不追求生成过程确定性，但保证**每个交付产物**的正确性和性能。用门控隔离而非消除非确定性。

```
generate → 门1 结构（输出指纹精确匹配，或形状指标在容忍带内）
         → 门2 正确性（参考模型差分，短/长负载逐产物）
         → 门3 性能（同 session 交错 5 对 vs 冻结基线产物，候选均值 ≤ 基线 × 1.03）
         → 失败处置：重生成 ≤2 次 → 回退冻结产物 → 必须报告形状指标
```

**案例实现要点**：
- 注册表 JSON：记录最优产物的指纹、形状指标、同 session 基线耗时、冻结的产物文件。
- 门 3 实测有效：一个确定性配置（慢 +22.4%）被正确拒绝；已知最优配置（+1.96%，噪声内）正常通过——**门要同时验证"能拒绝坏的"和"能放过好的"**。
- 内容键确定性保留为工具选项（非默认）：需要可复现调试时开启。

### 5.4 模式选择决策表

| 场景 | 推荐模式 | 理由 |
|---|---|---|
| 开发调试需要可复现 | 内容键比较器 + 带告警回退 | 确定性无需 seed，代价是形状税 |
| 交付最优性能产物 | 冻结产物 + 三道门 | 零形状税，非确定性用门控隔离 |
| 需要确定性 + 零税 | exact replay | 记录而非推导；实现复杂但案例已验证可行 |

## 6. 容器选择清单

在图算法中使用指针键容器前的检查项：

- [ ] 该容器是否只用于 find/insert/count（仅成员性）？如果是，指针序无语义风险。
- [ ] 是否有任何位置读取 `begin()` / 迭代序 / 排序后的首元素？如果有，指针序成为语义输入。
- [ ] 是否有贪心资格判定以容器导出的 `order`/`rank` 为输入？如果有，资格判定本身随布局变化。
- [ ] 是否有"代表选择"（取集合中某个元素作为合并目标/发起者）？如果有，选择结果随布局变化。
- [ ] 替换比较器后，新键是否对所有同时存活的 distinct 节点构成严格弱序？否则会静默丢节点。
- [ ] 末位 tie-break 是否内容稳定？如果不稳定，是否有告警机制暴露回退被命中？

## 7. 未决问题与残余（案例记录）

1. **默认配置下游分叉**：未加优化配方的模型跨分配器仍不同（生成头文件的状态字段差异），分叉点在复制 pass 之后（未定位）——交付配方路径不受影响。
2. **拓扑排序遍的死内容分叉**：死节点内容跨分配器不同（死代码消除后收敛，无语义影响）——清理候选。
3. **门 3 基线的长期管理**：性能门基线随机器漂移，需周期性同 session 复测更新。

## 8. 模式补充：两阶段交错传播

除了"单容器指针序迭代"这一病灶，**两阶段传播交错在同一循环里**同样致命——而且后果更严重。

### 8.1 机制

阶段 B 的传播读取阶段 A 构建的状态，而 A 尚未对全集完成：

```cpp
// 案例修复前：checkNodes 是指针序 std::set<Node*>
for (Node* n : checkNodes) {
  n->updateConnect();              // 阶段 A：n 的消费者边 -> 其他节点的 next 集
  if (n->type == NODE_REG_SRC) n->updateDep();  // 阶段 B：读 R->next 传播 reset dep 边
}
```

`updateDep(R)` 把 reset 的 dep 边传播给 `R->next` 里的**所有**节点；若 R 的 updateDep 在某个消费者的 updateConnect 之前执行，该消费者就**永久丢失**这条 dep 边。指针序决定交错顺序 → **同输入跨 run 的 dep 边集不同**（案例实测：reset → state$NEXT_{1,12,13,14} 边时有时无；某 reset 节点的依赖集在不同 run 为 2 / 4 条，修复后完整为 160 条）。

### 8.2 与指针序消费模式的区别

| | 指针序消费 | 两阶段交错 |
|---|---|---|
| 病灶 | 迭代序直接进入决策 | 迭代序决定**读取的状态是否完整** |
| 后果 | 同一输入不同合法输出 | **输出可不完整**（丢边），不只是不同 |
| 对指针序的依赖 | 必然 | 只要容器无序即触发；名字序容器是"确定但不完整"的同族 bug |
| 修复 | 换内容键比较器 | **拆成两遍循环**（先全 A 后全 B）——不是换序，是消除交错 |

### 8.3 检测与修复

- **检测**：exact-replay 的逐点 canon 门在拓扑排序遍报内容分叉；记录级 dump 逐字段 diff 定位到 dep 字段与具体节点。注意本例普通连接边从不变、**只有 dep-only 边变**——字段选择性本身就是定位线索（dep-only 边的构建点 = 阶段 B 的传播函数）。
- **修复**：两处交错循环（AST→图构建、数组分裂）都拆成两遍。修复后 4/4 次全模型生成 canon 全同。
- **名称序不是免罪牌**：案例中 AST→图构建的交错循环用的是 `std::map<std::string, Node*>`（确定序），但对名字排序晚于寄存器的消费者**确定性丢边**——交错本身是 bug，与容器序无关。

### 8.4 影响面评估清单

两阶段交错在图处理代码里的通用识别特征：

1. 循环体内先调用"构建连接/状态"函数、再调用"读取他人状态做传播"函数；
2. 传播结果写回图（不是局部变量）；
3. 容器是 set/map（任何非语义全序）。

命中三条即按两阶段交错处理：拆两遍 + 跨 run canon 复测。

## 9. exact replay v2 操作模式

**写种子**（被动记录，不改变生成行为）：

```bash
GEN_SEED_WRITE=/path/best.genseed \
  mygen <flags> --dir <model-dir> <input>
# 日志应有 [seed] recorded <tag> × N + 退出时 wrote ...
```

**回放**（逐点强制 + canon 校验链）：

```bash
GEN_SEED=/path/best.genseed \
  mygen <完全相同的 flags> --dir <out-dir> <input>
# [seed] applied <tag> (k/N) 逐个出现；跨分配器验证用 LD_PRELOAD=libjemalloc.so.2
```

操作要点（都是案例实测踩过的坑）：

1. **flags/配方必须逐字一致**：种子只钉序与内容，不编码配方；canon 门会抓配方漂移（断言消息指名分叉点）。
2. **输出目录必须先存在**（发射器不创建目录）。
3. **环境污染**：生成器环境变量残留在 shell 里会让小模型冒烟莫名断言——冒烟测试用 `env -i` 从干净环境跑。
4. **canon 覆盖范围 = 可验证范围**：主排序容器之外的容器（reset 表、实例表、JSON 元数据）只有字节级终验能覆盖；案例的 6 个交错 bug 里有 3 个是字节比对才暴露的。
5. **种子与生成器同生共死**：生成器任何影响内容的修改后必须重录；种子文件不跨二进制版本复用。
6. **体积**：大模型的逐点排列记录可达 GB 级（案例：9 钉点 / 7.2M interned 名，~1.5GB 未压缩）；需要二进制/压缩格式（案例预计 zlib 后 ~300MB）。

## 10. 级联效应：内容修复会改变调参地貌

修复生成器内容 bug 后，**所有在旧（有 bug）内容上调过的旋钮都要重扫**——旧最优点是建立在错误结构上的。

### 10.1 案例实测链条（全部因果对照）

1. **修复本身直接改性能**：32 线程配置修复前 vs 修复后同配方 = **−15.95%**（缺失的 dep 边让图收缩欠约束，宽配置的拒绝空间放大效应）；16 线程同修复仅 +0.68% 中性——紧约束下欠约束无从作恶。**同一 bug 对不同配置的杀伤力可以差一个量级。**
2. **旋钮最优集体迁移**：任务数上限旋钮（MAXMT）在修复前边集上 32T=3200 / 16T=2000；修复后 **32T→2400（−2.6%）、16T→800（−10.45%）**。机理：边集补全后，欠约束时期需要的"更多合并来兜底"的压力消失，更紧的上限（更少任务 = 更少 token/分发开销）变得可行。16T-800 比 16T-1600 少 28.5% DAG 边、21% 更少任务，层数与临界路径不变。
3. **地貌非光滑**：32T 在 2800（+27.7%）比 3200（+4.1%）差得多；16T 在 400 处 +36.3% 悬崖。修复后的地貌同样是混沌的——只能逐点实测，不能外插。

### 10.2 操作规则

> **任何改变生成内容的修复（不只是顺序，还包括边补全、语义修正）落地后，第一优先级是把影响面内的旋钮重扫一遍（至少最优点 ±1 档），再谈新探索。**

### 10.3 反向应用

"修复后地貌不变"也是可证伪的假设：案例 16 线程的因果对照（+0.68% 中性）证明修复对该配置几乎无结构影响——但旋钮重扫仍然发现了 −10.45%。**修复效应与旋钮效应可以分别归属**——这正是同配方因果对照的价值。

### 10.4 修复后地貌示例（16 线程，任务数上限扫描）

| 上限 | ms | vs 最优 | 任务数 |
|---|---|---|---|
| 400 | 8,790.8 | +36.3%（悬崖） | 7,260 |
| **800** | **6,431.4** | **最优** | 8,436 |
| 1200 | 6,665.4 | +3.6% | 9,699 |
| 1600 | 7,063–7,182 | +9.8% | 10,734 |
| 2000 | 7,296.7 | +13.4% | 11,583 |
| 2400 | 7,378.2 | +14.7% | 12,275 |

机理读法：从松到紧，收益来自 token/分发同步开销削减；悬崖来自并行度枯竭（任务数/worker 太少）。worker 翻倍时悬崖更早出现。

### 10.5 删除界 ≠ 可实现界

对循环结构做"删掉某类节点能降多少迭代下界"的预检时，得到的是**数学上界，不是工程上界**。可实现性必须过"语义保持变换存在性"论证（案例）：

| 变换 | 对循环迭代下界的作用 | 可实现性 |
|---|---|---|
| 融合/重划分 | 不变（环上工作量守恒） | 只改变调度灵活性，降不了下界 |
| 复制 | 不变（环上保留一整份） | 只削扇出，降不了下界，还加总量 |
| 流水化（环距离 1→2） | 比值减半 | **改变仿真语义**——参考模型判定失败 |
| 删除节点 | −25.88%（实测上界） | **无任何语义保持变换对应** |

结论模板：**迭代下界 ≈ 总工作量/线程数 的模型里，单边优化是零**（下界降了工作量界接管；工作量降了下界接管）。案例的 16 线程最优配置恰好两者比值 1.00——两个界必须同时打，而同时打两条界通常意味着改输入语义（出工具域）。
