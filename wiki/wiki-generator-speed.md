# 生成器速度工程：前提验证与守恒门

## 概述

生成代码仿真器上，"生成一次"坐在每一次实验的关键路径上：A/B 两侧各是一次完整生成 + 编译（分钟到小时级），调参扫描、种子重录、回归门禁全部按生成次数付费。生成器变慢直接收缩每天可做的实验数，所以生成期优化（generator-speed engineering）本身就是一类值得系统对待的工程。

但它有两条普通性能工程没有的约束：

1. **输出必须守恒**：任何加速不得改变生成的模型内容——否则全部历史基线作废、所有种子失效（见 [[wiki-pointer-order-nondeterminism]] §9"种子与生成器同生共死"）。速度收益与输出恒等必须在**同一次改动**里交付，不存在"先快后对"的过渡态。
2. **前提必须实测**：生成器内部的成本结构（哪个 pass 占多少）没有可靠直觉。案例中一个被普遍默认为"文本格式化"的收尾阶段，装上阶段计时器后证明发射本身只占该阶段的 1.6%，真实成本是调度构建，外加一个藏在调试 JSON dump 背后的重复构建。

本文按一次真实生成期优化战役的完整链条组织：前提检查（§1）、canon 哈希并行化（§2）、合并循环调度构建（§3）、生成器改动的确定性门禁（§4）、检查清单（§5）。与 [[wiki-value-change-census]] 的关系：那是"census before emit"用在**运行时生成的代码**上，本文是同一条纪律用在**生成器自身**上——先数清成本，再动手。

## 1. 前提检查：阶段计时器先于优化

### 1.1 事故形态：一个从未被测量的"格式化"阶段

案例：一次完整生成耗时 44 分钟，收尾的"Final"阶段被团队默认为文本发射/格式化成本——这个前提从未被测量，却已经在指导优化讨论（"优化发射器/减少字符串拷贝"）。装上按阶段的墙钟计时器后：

| 前提 | 实测 |
|---|---|
| Final ≈ 发射/格式化 | **发射仅占 Final 的 1.6%** |
| （未被讨论） | 真实主体是**调度构建**（合并循环，见 §3） |
| （完全不可见） | 调试 JSON dump 背后藏着一次**重复构建**——dump 路径为了输出元数据，把已经建好的图结构重新构建了一遍 |

三个可迁移的判定点：

1. **未插桩区域 = 未知，而不是"琐碎"**。一个阶段没被计时，它就是总时长减去其它阶段的余项——把余项贴上"格式化"标签是命名，不是测量。
2. **调试/dump 路径是一等成本中心**。dump 为了输出而**重建**状态，等于把构建成本付两遍；dump 必须只读既有结构，或者用开关彻底门控。
3. **阶段名必须对应成本中心，而不是代码地理位置**。"Final" 这种按代码布局命名的阶段会吞掉一切没有单独插桩的工作。

### 1.2 纪律

**任何"瓶颈是 X"的前提，先装粗粒度按 pass 墙钟计时器再谈优化。**这件事零风险（不改变行为）、成本低（每个顶层 pass 一对时间戳），而且答案经常推翻共识——案例中前提（发射为主）与实测（发射 1.6%）之间差了两个数量级。这与 [[wiki-value-change-census]] §1 的"反事实不可推断"同构：比例（成本分布）是管线的联合属性，不能从代码外观推断，只能到真实执行的阶段上去数。

> 顺带的教训：**计时器本身按阶段输出，就顺带成为后续优化的回归基线**——§3 的每一次改动都能立即看到"Final 占比"是否真的下降了。

## 2. canon/identity 哈希的按记录并行

### 2.1 机制：order-free 是并行化的恒等条件

生成器的 canon/identity 哈希（对图状态做 order-free 内容哈希，用作确定性门禁与指纹，见 [[wiki-pointer-order-nondeterminism]] §4.2/§4.3）天然可并行，**且输出与串行版逐位相同**。原因是构造性的：

- 哈希定义在**排序后的记录序列**上：每条记录（成员名 + 排序端点名，排除 id/地址等不稳定字段）先做独立的逐记录摘要，再按**内容排序**的顺序折叠成总哈希。
- **排序使构建顺序无关**：总哈希只依赖记录内容集合，不依赖记录的插入/构建顺序。既然串行版的输出本来就不含顺序信息，把逐记录摘要分给多线程、再在规范序上合并，结果**必然**逐位相同——分片方式、线程数、调度时序都不进入输出。

### 2.2 与"顺序敏感但当前确定"的本质区别

并行化一个函数前必须先分类：

| 类别 | 判据 | 可否无门并行 |
|---|---|---|
| **order-free（按定义）** | 输出在数学上与处理顺序无关（排序后折叠、交换律合并） | **可以**——恒等是定理不是假设（本节案例） |
| 顺序敏感、但当前确定 | 输出依赖处理顺序，当前靠单线程/稳定容器保持一致 | 不可以——并行会改变输出，需要 §4 门禁 + 明确的顺序设计 |

把第二类误当第一类是生成器并行化最常见的静默事故：单线程下"恰好确定"掩盖了顺序依赖，多线程一开，输出开始漂移，而漂移要到字节比对/canon 门才被发现——离引入点已经隔了整条管线。

### 2.3 附带收益：并行化不弱化门禁，反而被门禁自检

canon 哈希本身就是确定性门禁（[[wiki-pointer-order-nondeterminism]] §4.3 的规范化指纹二分用的正是它）。并行化它不会弱化门禁：哈希的 order-free 定义不变，任何实现错误（比如合并时引入了顺序）都会让 canon 点在种子回放中立刻分叉——**门禁守护的函数自己也被门禁守护**。工程要点：

- 逐记录摘要的字段排除表（地址、分配序 id、指针值）必须与既有 canon 二分器完全一致，否则新旧哈希不可比；
- 合并用规范序折叠（或交换律算子），但**不要**同时改字段集——一次改动只动并行化，字段语义冻结，新旧实现才能在同图上对拍。

## 3. 合并循环调度构建：数据结构与查询的联合优化

§1 的计时器把"Final"的主体定位到调度构建（合并循环）。这一节的两个落地优化和一个被证伪的捷径。

### 3.1 数据结构：`std::set` 关系集合 → 排序平铺向量

合并循环把关系集合（邻接/依赖集）放在 `std::set` 里：每次成员测试付红黑树指针跳转 + 每个节点一次堆分配，缓存局部性差。换成**排序平铺向量**（一次构建、排序、之后二分/归并），去掉逐节点分配并恢复顺序扫描局部性。

与 [[wiki-pointer-order-nondeterminism]] §2 的衔接：`std::set<T*>` 的默认迭代序是指针序——排序平铺向量**顺带消除了这个非确定性隐患**，前提是排序键必须是内容键（成员名/行号类），而不是地址。一个性能改动同时是确定性修复，两个动机都写进 commit，避免后人"优化"回 `std::set` 时只看到性能理由。

### 3.2 查询：可达性/路径查询占 77% → 按合并代备忘录化

计时器进一步显示调度构建内部：**可达性/路径查询占整个生成的 77%**——合并循环的每一步都要在当前 quotient 图上问"X 可达 Y 吗"。优化不是换更快的搜索，而是**消掉重复提问**：

- quotient 图只在合并时变化。以**合并代**（merge generation）为缓存键：同一代内所有可达性结果不变，跨代作废重算。
- 缓存键必须枚举结果依赖的一切（图代数），这正是缓存正确性的全部条件——见 §5 检查清单第 7 条。

备忘录化把查询成本从"每次提问都遍历"压到"每代首次提问遍历"，而且**答案不变**（同一代上图相同 ⇒ 同一问题同一答案），因此它像 §2 一样是恒等保持的优化，只需 §4 的门禁确认实现无 bug。

### 3.3 被证伪的捷径：quotient 图上的双向搜索

可达性占 77% 时，双向搜索（从源正向、从汇反向，相遇即停）看起来是教科书式加速：搜索深度减半，期望平方级提速。**它在 live quotient 图上不 sound**：

- 双向搜索的正确性前提是：反向遍历用的前驱关系 gP 是正向后继关系 gS 的**精确逆**——每条正向边都有对应的显式反向边，粒度一致。
- 合并群打破这个前提：节点并入超级节点后，边的可见性在两个方向上**不对称**——反向边可能只以群粒度存在、或者根本没有被显式建出来。gP ≠ reverse(gS)。
- 后果：双向搜索会**漏路径**——返回"不可达"而单向搜索返回"可达"。这不是"更快地算出同一个答案"，是**算出不同的答案**：调度构建的合并决策直接被改变，输出不再恒等。

判定与处置（每一步都可迁移）：

1. **对派生/quotient 结构做算法替换前，先证它需要的不变量**——而且要在**经历全部变更（合并）之后的 live 结构**上证，不是在原始图上证。原始图上 gP = reverse(gS) 成立不代表合并后成立。
2. **用差分 harness 证伪**（§4.3）：把纯决策函数抽出来，旧新实现在同输入上对拍，合并群/不对称边这类对抗性输入一打，答案分叉立现。
3. **带证据回滚，先于 commit**：探针被测量、被证伪、被回退，证据（哪些输入上分叉、为什么）记录在案——与 [[wiki-ab-isolation-discipline]] §2 的撤回链同构，只是这次撤回发生在**测量之前**的 harness 阶段，成本便宜两个数量级。**会改变答案的"加速"不是加速**，永远不上 commit。

### 3.4 处置总表

| 改动 | 类型 | 输出恒等？ | 依据 | 处置 |
|---|---|---|---|---|
| canon 哈希按记录并行 | 并行化 order-free 函数 | 是 | 构造上成立（§2） | 落地 |
| `std::set` → 排序平铺向量 | 数据结构替换 | 是 | 内容键排序（§3.1）+ §4 门验证 | 落地 |
| 可达性按合并代备忘录化 | 缓存 | 是 | 缓存键 = 图代，同代图不变（§3.2） | 落地 |
| 双向搜索替换单向搜索 | 算法替换 | **否** | gP ≠ reverse(gS)，漏路径（§3.3） | harness 证伪 → 回滚 → 记录 |

## 4. 生成器改动的三重确定性门禁

生成器速度改动与 [[wiki-ab-isolation-discipline]] §1.1 的 flag-off 恒等有一个关键差异：**那里每个新特征有默认关闭态可回退，这里速度优化没有"关"**——加速必须无条件保持输出恒等，否则等于永久改写了基线。因此门禁是无条件的，且三道各司其职：

### 4.1 门一：字节恒等模型

改动前后各做一次完整配方生成，对**全部生成源文件**逐字节 diff（外加小设计集与分片并行构建）。这是端到端的最终判据：任何一道下游门漏掉的漂移都会在这里暴露。局限：粗粒度——分叉了只能告诉你**有**漂移，定位要靠门二。

### 4.2 门二：种子回放 canon 点

用既有种子回放（[[wiki-pointer-order-nondeterminism]] §5.2/§9 的逐点强制 + canon 校验链），在**钉住的中间点**上比对 canon 哈希。它把"生成器被我改坏了吗"从端点问题变成逐 pass 问题——第一个分叉点直接指名肇事 pass。种子必须与改动后的生成器**重新录制对拍**（旧种子只在旧二进制上有效）。

### 4.3 门三：纯决策函数差分 harness

把调度构建的决策逻辑抽成纯函数 harness（给定图状态，输出合并决策/可达性答案），旧新实现在相同输入序列上对拍：

- **成本结构逆转**：harness 跑秒级，完整生成跑分钟到小时级。它把"改坏了没有"从昂贵的端到端问题变成便宜的单元问题——§3.3 的双向搜索正是在这里被证伪，而没有消耗任何一次完整生成。
- **对抗性输入是 harness 的价值所在**：模型语料未必覆盖合并群/不对称边这类边界；harness 可以直接构造。语料能过的差分不等于 sound，专门设计的边界输入才能翻出 gP ≠ reverse(gS) 这类结构缺陷。
- **它同时是优化的证据链**：harness 上记录的缓存命中率/答案一致数，就是 §3.2 备忘录化收益的直接度量。

### 4.4 三道门的分工

| 门 | 覆盖 | 粒度 | 成本 |
|---|---|---|---|
| 字节恒等模型 | 端到端全部输出 | 有/无漂移 | 两次完整生成 |
| 种子回放 canon 点 | 逐 pass 中间状态 | 哪个 pass 分叉 | 一次生成 + 回放 |
| 决策函数差分 | 被改算法本身 | 哪类输入分叉 | 秒级 |

三道门缺一不可：只有门一，定位靠盲猜；只有门二，算法层的结构缺陷要等语料撞上；只有门三，集成层（发射、序列化）的漂移无人看守。

## 5. 检查清单

1. 优化讨论开始前，每个顶层 pass 一对时间戳；未插桩区域按"未知"处理，不贴标签。
2. 调试/dump 路径审计重复构建；dump 只读既有结构或被开关彻底门控。
3. "格式化/发射类"假设先拿数字（案例：发射占被指认阶段的 1.6%）再排期。
4. 只并行化**按定义 order-free** 的函数；"单线程下恰好确定"不是并行化许可。
5. 并行哈希的逐记录字段排除表与既有 canon 二分器逐项一致；一次改动只动并行化，不动字段语义。
6. `std::set` → 排序平铺向量时排序键必须是内容键；性能动机与确定性修复同时写进提交说明。
7. 缓存必须带显式失效键（合并代/图版本），且键枚举结果依赖的全部输入。
8. 对派生/quotient 结构替换算法前，先在**经历全部变更的 live 结构**上证明算法需要的不变量（gP = reverse(gS) 类）。
9. 证伪的捷径：harness 对拍证 unsound → 回滚先于 commit → 证据入库；会改变答案的加速不是加速。
10. 每个生成器速度改动交付三道门：字节恒等模型 diff + 种子回放 canon 点 + 纯决策函数差分 harness。

## 追记（2026-08-27）：陈旧表项 = 活边副本——假性环拒绝

合并循环的原始邻接表（gS/gP）里，被吸收群组的残留表项在 find() 规范化后成为**活边的重复副本**。候选评估协议是"临时擦除直连边再查 pathExists"——擦除按值删**一个**出现，死副本让直连边对 DFS 仍然可见 → pathExists 平凡命中 → 合并被**误判为成环**而拒绝。

T32 冠军图实测：cycRej **3,286,710 → 200,279（16×）**，merges 32,887 → 36,909，MTasks 12,275 → 8,253。更粗的调度反而**更快**：C50000 五对 5.008s vs 5.668s（-11.6%，区间不重叠），Linux 100K -8.4%。注册为新 T32 冠军（xiangshan-t32-compact-v1）。

三条可迁移判定：

1. **"中性"内部优化假设可能在信息量大的方向上错**——本例假设死表项压实只是提速，manifest 恒等门在性能声明**之前**抓到了调度变化，把一个静默的启发式缺陷转成 11.6% 的实测收益。恒等门不只是安全网，也是发现器。
2. **并查集 + 临时擦除的语义交互**要显式审计：擦除-恢复协议下，等价类代表元的重复计数不是无害冗余，它改变可达性查询的答案。
3. **更少的选择有时是更好的选择**：16× 的假拒绝一直在压制合并启发式；"拒绝率高 = 图难合并"的直觉可能是数据结构自伤的伪影。

配套修复纪律：门控默认关（注册冠军的调度建立在旧行为上）；配方 = 既有种子（钉点到 preEmit）+ 压实旋钮，vcontract 在钉点后自由运行——新调度是 (种子钉, 压实) 的确定函数，逐次运行字节一致；无种子的自由写在 jemalloc 下落在已知 splitArray 平局边界上（sccs 45161 vs 45162），配方必须走种子路径。


### 追记补：逐档位结局（2026-08-29 修正：两轮 T16 数据均为跨图污染）

**原始结论已被推翻。** T16 压实 +1.5% 与 +7.2% 两次测量均为跨分配器/跨图对比（jemalloc 二进制 vs glibc 图的冠军）。确定性修复后同图 A/B（同一二进制、sccs=45163 双侧一致）**翻转结论**：T16 压实 **-8.4% 更快**（{6.43-6.47} vs {6.94-7.13}，5 对不重叠）。

**修正后的教训**（比原教训更深一层）：在证伪模型之前，先验证证伪所依据的测量——跨图污染不仅使结论无效，也使"证伪"本身无效。本例中两项分数模型两次都选了 COMPACT（对的），我的"证伪加固"却建立在坏数据上。正确的等级是：测量有效性 > 模型验证 > 模型证伪。POLICY=auto 已回退纯分数规则。


### 追记补 2：输入自适应策略选择（2026-08-28）

用户点破的方向：**优化策略的选择本身应当是输入的函数**——理解每个优化的本质（它交换什么、付出什么），在任意 RTL/workload 输入下自动选出对症的那个。

压实旋钮的本质结构：
- **换来**：跨线程依赖边 -40~55%（同步点减少）
- **付出**：任务粒度变粗（均衡打包变难、fill/drain 变长）
- T32（同步开销绑定）→ 赢 11.6%；T16（工作地板绑定）→ 输 1.5%（合并后 7.2%）

`POLICY=auto` 的实现：代码生成期**双 pass 构建两个候选调度**（契约构建器自包含，第二遍从原始商图重启），用两项地板模型（真实列表调度器的 maxW + 边数 × 实测 token 延迟）评分选优。

**两次证伪的教训**（这是比成功更值钱的部分）：
1. 自由 LPT 评分分配器把 maxW 算成完美均衡——恰好抹掉了决定 T16 的那一项；
2. 换上真实依赖感知分配器后，模型仍选 COMPACT——因为缺失的 fill/drain 与粒度项**都反压实**，缺失项模型必然朝它缺失的方向错。
最终规则：**（线程数先验 ∧ 模型同意）的合取**。校准过的先验承载数据，模型只做高线程否决。

**方法论沉淀**：三点标定两常数的地板模型是假设不是策略；合取（校准先验 AND 模型）是缺失项未建模前的诚实折中。策略选择器的每一次升级都应来自一次新的证伪。
