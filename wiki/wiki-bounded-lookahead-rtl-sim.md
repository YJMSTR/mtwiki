# 静态调度 worker 链中的有界乱序填补

## 概述

许多编译出的并行执行器采用**静态调度**：任务图在编译期划分给固定数量的 worker，每个 worker 拿到一条按固定顺序执行的任务链；跨 worker 依赖用就绪 token 同步——链首（head）依赖的上游 token 未就绪时，worker 只能自旋等待。

这类结构的核心浪费是**队头阻塞**：链是全序，而链序里相邻两个任务之间往往没有真实数据依赖。head 一旦阻塞，链后方大量已就绪的独立任务也只能陪着等。

有界乱序填补（bounded lookahead / bounded out-of-order fill）是最小侵入的解法：head 阻塞时，worker 扫描链后方一个有界窗口，提前执行其中已就绪的条目，用独立工作填掉 stall 气泡；链序本身、任务归属、token 协议全部不动。

本文提炼该技术的一般设计（窗口就绪扫描、安全门、head 优先权、热路径/冷尾分层）与可迁移的实测教训。案例数据来自一个多线程 RTL 仿真器（gsim-mt，见文末）：约 45,000 个强连通分量收缩成 ~12,500 个任务、按关键路径分配到 32 个固定 worker，实测各 worker 有 43–67%（均值 ~50%）的周期处于空转——是该执行器性能的头号浪费源。

## 1. 核心洞察：固定链序的排序边绝大多数是保守的

对案例执行器 12,539 条链内排序边做可达性证明（编译期离线分析）：

| 类别 | 数量 | 含义 |
|---|---|---|
| 真实数据依赖 | 1,569（12.5%） | 必须保持顺序 |
| **保守边（无路径）** | **10,967（87.5%）** | 仅由链序保证，两端无真实依赖 |
| 间接路径 | 3 | - |

**通用结论**：静态调度器为了给每个 worker 造一条全序链，会把大量互不依赖的任务人为排序。head 阻塞时，链后方绝大多数条目与 head 之间不存在真实依赖——它们已经可以安全提前执行。这个比例（此处 87.5%）在任何"任务图 + 固定链序"结构里都值得先量化：它就是乱序填补的理论上限空间。

离线模拟（对执行序做理想化重放）：窗口 N=128 可消除 17.2% 的 makespan。

> **配套否决**：编译期链重排（按依赖深度 / 最早开始 / 跨 worker 前驱计数排序）全面更差（−19.1% / −44.2% / 不可行）。案例调度器的关键路径优先链序已是最优固定链序——**改善只能来自运行时乱序，不是换一种固定序**。

## 2. 协议设计

### 2.1 运行时流程

```
每拍开始: worker 进入内联 Phase 1
  ┌─ head 全部 token == target? ── 是 ── 内联直调 body + 内联释放 store list + head++
  │                                    └─ 回到检查
  └─ 否, 首个阻塞 ── 调用冷尾（完整表 + 全局 startHead）
                         ┌─ head token 就绪? ── 是 ── 执行 head + 立即释放 + head++ + 跳过已置位项
                         │                         └─ 回到检查
                         └─ 否 ── 扫描窗口 head+1 .. head+1+N
                                    ┌─ 候选 j: 全部 wait token 就绪 且 本地前置全部完成?
                                    │    └─ 是 ── 执行 j + 立即释放 + doneBit 置位 + 立即 break 重检 head
                                    │              └─ 回到 head 检查
                                    └─ 窗口扫完无进展 ── 对 head 阻塞自旋（256 poll/yield）
```

### 2.2 内联热路径 + 冷尾表驱动

| 路径 | 结构 | 原因 |
|---|---|---|
| **Phase 1（热路径）** | 内联直调 body、内联释放 store list | 全链改表循环会交 ~4% 税（案例实测 +4.02% 回退） |
| **冷尾** | 完整表 + 全局 startHead + 成员函数指针 | 仅在 head 首次阻塞时进入；表/位图只存在于冷尾 |

热路径保持与原执行器逐指令等价的内联直调，仅把阻塞自旋换成非阻塞就绪测试。**通用教训：给高频直线代码加乱序能力时，所有簿记结构（表、位图、函数指针）都必须留在低频冷路径里**。

### 2.3 三个安全门

候选 j 可执行 ⟺ 全部满足：

1. **跨 worker 门**：j 的 wait list 中全部 token == 当前拍 target（非阻塞读）。token 按 (destination, producerOwner) 分组，覆盖全部跨 worker 真依赖。
2. **同 worker 本地前置门**：j 的全部本地前置位置完成——判定式 `p < head || (anyOutOfOrder && doneBit(p))`。前置集 = 同 worker DAG 保留前驱 ∪ **publisher sibling**（见 §3）。
3. **head 优先权**：每执行一个候选立即 break 重检 head——head 在关键路径上，其启动延迟比扫描开销更贵。

## 3. 陷阱：不能直接复用"按序执行"时代的同步协议

把按序执行器改成乱序填补时，旧协议中所有**隐式依赖链序**的约定都要重审。案例中踩过三个：

| 陷阱 | 后果 | 解法 |
|---|---|---|
| 旧运行时归约注入了**合成链边**（`previousOnWorker->taskId`）后才做传递归约——删除只在全链有序下成立 | 乱序下被删的真实跨 worker 依赖裸奔，消费者读过期数据 | **从原始任务 DAG（不含合成链边）重做仅 DAG 的传递归约**，用其重建 token 分组（13,679–14,116 组 vs 原 5,195，建模回归仅 +3.06%） |
| 分组 token 的释放只由组内链序最后的 source（publisher）执行；publisher 乱序先于同组独立 sibling → 提前发布 | 消费者在全部组内生产者完成前读取 | **publisher-sibling 位置物化为本地前置**（909 条目 / 3,163 位置，建模代价 <1%） |
| 表驱动常路径（成员函数指针）实测 +4.02% | 把全链改表循环会交 4% 税 | **内联 Phase 1 + 冷尾**（见 §2.2） |

### 3.1 chain-aware 传递归约为何在乱序下不成立

旧协议的传递归约依赖合成链边 `previousOnWorker->taskId`：它假设全链按序执行，因此链上相邻条目间的跨 worker 依赖可以通过链边传递到达，无需直接保留。但在乱序执行下，链边不再是执行顺序的保证——被链边"覆盖"删除的真实跨 worker 依赖会裸奔，消费者可能在生产者尚未执行时读取过期数据。

**解法**：从原始任务 DAG（不含合成链边）重做传递归约。代价是 token 组数从 5,195 增至 13,679–14,116（更多组 = 更多 token），建模回归仅 +3.06%——正确性约束换来的同步开销是可承受的。

## 4. 正确性论证要点（6 条引理）

1. **链序即拓扑序**：同 worker 真依赖 pred→succ 满足 position(pred) < position(succ)。
2. **仅 DAG 归约保可达**：token + 本地前置覆盖全部全 DAG 前驱。
3. **publisher 约束保证释放不会早于其代表的全部写入**。
4. **head 无需检查**（head 性质）；候选须过三个安全门的全部。
5. **完成归纳**：任意完成 ⟹ 其全部全 DAG 前驱完成（跨 worker happens-before 与严格序相同）。
6. **确定性**：扫描升序、首合格即执行、独立条目可交换。

> **经验证据的形态**：案例用两层验证——结构性论证（上述引理）+ 重复运行端点一致性（短/长负载各 100 次重复、参考模型（ISA 级 golden model）差分全过、端点全一致）。stdout 帧内容的非 bit 一致属于打印行序类可观测分歧，只要端点状态不受影响即可豁免（层次划分见 [[wiki-pointer-order-nondeterminism]] §1）。

## 5. 实测收益（案例数据）

测量纪律：全部产物通过参考模型差分（短负载 ~5K 指令、长负载 ~50K 指令）、固定负载交错 A/B（消除 cache/频率漂移）、非重叠采样。

### 5.1 主结果

| 负载 | 对照（无前瞻） | LOOKAHEAD=128 | delta |
|---|---|---|---|
| CoreMark 长负载 | 7,177.7ms | **6,329.7ms** | **−11.81%** |
| Linux 启动 100K | 14,466.0ms | **12,644.3ms** | **−12.60%** |
| Linux 启动 1M | 142,674.7ms | **126,232.7ms** | **−11.52%** |

### 5.2 机制证据（perf 计数器）

| 指标 | 对照 | N=16 | N=128 |
|---|---|---|---|
| 指令数 | 262.3G | 318.9G | 505.2G |
| **IPC** | **0.31** | **0.42** | **0.69** |
| 分支误预测率 | 1.20% | 1.19% | 0.91% |

**收益机制**：head 阻塞时 worker 不再空转，转去执行链后方已就绪的条目——stall 被填掉（IPC 0.31→0.69）。扫描/簿记指令虽然多（最高 +92.6%），但运行在否则闲置的 stall 周期里。分支预测不受影响（冷尾的表间接未表现为误预测）。

**通用教训：乱序填补的簿记开销可以远大于净收益的量级而不亏——只要这些指令消耗的是本来闲置的 stall 周期。判断标准是 IPC（或周期数），不是指令数。**

### 5.3 收益归因：依赖 stall 消除，不是带宽再平衡

perf 专项（对照 vs N=128）：

| 指标 | 对照 | N=128 | delta |
|---|---|---|---|
| cycles | 842.5G | 742.2G | −11.9% |
| **stalled-cycles-backend** | **228.3G（27.09%）** | **158.2G（21.31%）** | **−30.7%** |
| stalled-cycles-frontend | 2.38G（0.28%） | 2.67G（0.36%） | +12% |
| cache-references | 31.4G | 30.1G | −4.0% |
| cache-misses | 13.1G（41.75%） | 12.8G（42.59%） | −2.1% |

周期下降的 ~70% 来自**后端 stall 消除**（228.3G→158.2G），而访存流量几乎不变（misses −2.1%、miss 率持平 41.8%→42.6%）。若机器受 DRAM/L3 带宽饱和约束，不可能在流量不变下削掉 30% 后端 stall——**带宽本来就有余量**。stall 的本质是跨 worker token 的依赖等待，前瞻用独立条目的工作（连同其访存，现在被重叠发射）把气泡填掉。"计算与访存重叠"只在 MLP 重叠这个有限意义上成立，**不是 roofline 式再平衡**。

**方法论**：证明"收益来自 X"要同时给出 X 的直接计数器证据（stalled-cycles 大降）与非 X 的反证（带宽指标不动）。只看 wall time 无法区分 stall 消除与带宽再平衡。

## 6. 窗口 N 的选择

### 6.1 实测扫描（同一调度的双生构建，仅窗口字面量不同）

| N | CoreMark 均值 | Linux 100K 均值 | 指令数 |
|---|---|---|---|
| 16 | 6,483.0ms | - | 318.9G |
| 32 | 6,406.0ms | 12,717ms | - |
| 64 | 6,350.7ms | **12,583ms** | - |
| 128 | 6,355.3ms | 12,888ms | 505.2G |
| 256 | **6,294.7ms** | 12,660ms | - |

### 6.2 结论：宽平台、弱负载相关

- **宽平台**：N=64–256 在两种负载下互相差距都在 ~2%（噪声级）。
- **弱负载相关**：精确最优点随负载移动——CoreMark 偏好 ≥128（stall 深、就绪窗口利用率随 N 增大仍有微益），Linux 偏好 ~64（依赖链更短、IPC 更高，过大窗口的扫描开销开始抵消收益）。**这不是强相关：取 N∈[64,128] 在两类负载上都接近最优**。
- **指令效率视角**：N=16 用 63% 的指令数拿到大部分收益（−9.68%）；若未来 CPU 吞吐成为瓶颈（共享机器、超售），小窗口是指令效率最优点。
- **默认值不必是精确最优**：案例默认 N=128 处于平台内，离两个负载各自的实测最优都在噪声范围。窗口参数是宽平台参数——调优收益 ~2%，不值得反复重调。

## 7. head 优先权与批量执行否决

**批量扫描变体（cap 4）**：执行最多 4 个合格候选后再重检 head，以减少重扫开销。

| 指标 | cap-1（break 重检） | cap-4（批量） | delta |
|---|---|---|---|
| 长负载均值 | 6,302.0ms | 6,787.3ms | **+7.71%** |

**隔离**：不可变调度双生（`diff -qr` 仅 1 文件 23 行差异 = 批量改动本身）、12,571 任务调度一致、产物大小一致、全部 6 次参考模型差分通过。

**结论**：head 优先权代价远超重扫节省。head 在关键路径上，其启动延迟比省下的扫描指令更贵。**通用教训：乱序填补协议里"尽快回到队头"不是开销，是收益的一部分。**

## 8. 被否决的替代设计（选型证据）

| 设计 | 结果 | 教训 |
|---|---|---|
| **仅 DAG token + publisher 约束（采用）** | +18.2% 建模 / +11.8% 实测 | - |
| witness-safe（现 token + 仅无链见证删边者可乱序） | +0.5%，自由塌缩（71.1% 条目带见证删边） | 保守利用链序不可行 |
| epoch 混合（每任务 epoch + 逐个前驱 epoch 扫描） | 访存延迟 ≥40ns 或前驱比例 ≥0.25 即亏；候选确认读数 4× 于分组 token | 逐前驱远程读太贵，分组是压缩 |
| producer counting（每边 fetch_sub） | 17,663 RMW/拍，全面劣于分组 load/store | 单写者结构不可放弃 |
| 批量扫描（cap 4） | +7.7% 回退（不可变调度双生隔离） | head 优先权 > 重扫节省 |
| 表驱动常路径 | +4.02% 回退 | 表/指针只能进冷路径 |
| 等待期预取 | +4.67% 回退 | 预取循环指令开销超过隐藏的 L2/L3 延迟 |
| 提前释放（release-point f=0.5/0.7/0.9） | −0.45%/+0.00%/+0.27%，预检否决 | 前瞻已重叠大部分生产者延迟 |
| LPT 静态分配 | 离线模拟：按序 9,436.7 vs 7,411.5，前瞻后 6,997.4 vs 5,711.3——全面更差 | 关键路径分配优于 LPT |
| worker 内链重排（cp/成本序） | 按序 11,740 vs 7,411——更差 | 前瞻下复现：现关键路径优先级已最优 |

### 8.1 等待期预取详细否决

**设计**：head 阻塞自旋时预取跨 worker 生产者状态字段（按编译期已知字段偏移），重叠 L2/L3 延迟。

**机制评估**：成立（stall 为 µs 级，预取有充足时间；stall 是延迟非带宽）。

**实测**：{7,960, 7,883, 7,770} vs 对照 {7,627, 7,553, 7,378}，**+4.67% 回退**。同调度双生（调度指纹一致）、全部参考模型差分通过。8,916 列表条目 / 459,740 offsets：每次阻塞的预取循环指令开销超过其隐藏的 L2/L3 延迟。

**通用教训：机制上成立的优化仍可能因"每次等待的条目数 × 每条目的预取指令数"而净亏——簿记密度决定这类优化的生死，先算每次事件摊到多少条指令。**

## 9. 动态化评估（离线模拟）

| 方向 | 机制 | 结果 | 结论 |
|---|---|---|---|
| 运行时自适应窗口 N | 按 stall 深度动态调窗口 | 受宽平台限制（N=64–256 实测互相 ~2%） | 上限 ~2%，边际收益不抵策略复杂度 |
| 动态候选选择（maxcp / maxcost） | 窗口内选最关键候选而非升序首个 | N=128 maxcp 5670.8 vs first 5711.3（仅 +0.7%）；maxcost 更差（5765.3） | 首合格升序（零比较开销）已近最优 |
| 跨 worker 动态（窃取/迁移） | 打破固定 owner | owner-ready 协议语义依赖固定归属 | 大改无证据基础 |

**结论**：有界乱序填补的杠杆有结构性上限（案例 ~12%）；动态化变体合计 ≤1–2%，不构成下一步。**判断一个优化方向是否"结构性耗尽"：把已否决变体的机制族谱列全，若每个家族都有实测否决证据，转向其他杠杆类。**

## 10. 工程落地与验证纪律

- **默认关闭**：新调度行为做成编译期开关、默认关闭；开关关闭时生成产物与无开关版本逐字节一致（byte-identical）——这是可归因 A/B 的前提。
- **独立 checker**：另写一个从原始 DAG 重算"仅 DAG 传递归约"的检查器，核对生成器发射的全部 token 组/前置——不信任生成器自查。
- **正确性门**：参考模型差分（ISA 级 golden model，短/长负载）+ 100 次重复确定性检查。
- **性能门**：固定负载交错 A/B（同一 session 内交替跑对照/候选），不用跨日数据下结论。
- **变体实验**：克隆生成模型、只改窗口字面量，即可得到"同一调度、仅协议参数不同"的双生构建——把调度差异从协议实验里隔离出去。

## 11. 经典系统机制适用性裁决

把硬件/OS 的经典机制逐个映射到这类执行器上评估（案例实测）：

| 经典机制 | 在此类执行器中的对应 | 结论 |
|---|---|---|
| 分支预测 | 预测 token 就绪 | 硬件 BP 已覆盖（误预测率 0.91–1.20% 且前瞻后更低）；软件预测 token ≈ 前瞻本身。**不适用** |
| 页表/TLB | 大页、地址间接 | dTLB miss 率实测 0.07–0.09%——**实测非问题** |
| 乱序执行（深化） | 全局 OOO/中心就绪队列 | 通知开销杀死全局动态调度（离线否决）；worker 内 OOO 即前瞻（已落地）。**不扩展** |
| 投机执行 | 按旧值投机 + 回滚 | 同步 RTL 每拍所有触发器都更新，投机恒错且回滚代价高。**不成立** |
| 计算通信融合 | 等待期重叠通信与计算 | 前瞻本体即此类；延伸候选（预取/提前释放/重分配/重排）全部已否决 |

有界乱序填补（worker 内有界 OOO + 分组 token）是案例证据下唯一 ≥10% 的调度类杠杆。后续性能工作应转向非调度类杠杆。
